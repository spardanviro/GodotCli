# 架构与决策

线上协议见 [protocol.md](protocol.md)，阶段安排见 [roadmap.md](roadmap.md)。

## 目标

从 Claude（以及任何能跑命令行的智能体）里直接控制 Godot 做开发，对标 Unity 官方的 `unity` 命令行加 Claude 插件。

```
Claude Code ──(技能)──> gd 命令行 ──┬─(本机 HTTP + 令牌)──> 编辑器里的桥接 ──> 编辑器
     └──────(MCP)──────────┘        └─(启动子进程)────────> Godot 可执行文件
```

## 仓库布局

| 目录 | 内容 | 语言 |
|---|---|---|
| `bridge/` | 一个用于开发和测试的 Godot 项目；`bridge/addons/gdcli/` 是发布到资源库的桥接插件 | GDScript |
| `cli/` | `gd` 命令行，npm 包 | TypeScript |
| `plugin/` | Claude 插件：技能和参考资料 | Markdown |
| `docs/` | 协议、架构、路线图 | — |
| `scripts/` | 仓库级检查脚本 | Node |

三样东西放一个仓库，是因为它们共用一个协议号，必须一起改、一起发布。

## 已定决策（2026-10-09）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 桥接用 GDScript 编辑器插件，不用 GDExtension | 没有二进制，标准版 Godot 就能装，能上资源库；GDExtension 需要为每个平台编译 |
| 2 | 命令行用 TypeScript，经 npm 分发 | MCP 官方开发包最成熟；智能体所在环境几乎都有 Node |
| 3 | 新开仓库，原 `Godot_AI` 冻结并指向这里 | 原生模块要求自编译引擎，路线不同 |
| 4 | 最低支持 Godot 4.3 稳定版 | `--import` 等命令行能力从 4.3 起可用；持续集成覆盖 4.3 至 4.7 |
| 5 | 命令叫 `gd`，npm 包和插件目录叫 `gdcli` | `godot` 被引擎占用；见下文"命名" |
| 6 | 两条通道：离线（启动 Godot 进程）和在线（桥接） | Godot 自带命令行已经覆盖运行、检查、导入、导出、接口文档，不必经过桥接重做一遍 |
| 7 | 锁文件放用户目录，不做心跳，以握手判活；握手用 HMAC 证明对方持有令牌 | 令牌不进项目目录；少一个定时写盘；令牌不会发给冒名占用端口的进程 |
| 8 | 值用带标签的 JSON 编码，不用 `str_to_var`；不能凭空构造脚本 | 后者能构造任意对象，是一条代码执行旁路 |
| 9 | 访问模式存在编辑器设置里，不存在项目文件里 | 项目文件智能体改得了，克隆来的仓库也带得进来 |
| 10 | 风险分级明说是护栏不是沙箱；`standard` 模式下智能体有代码执行能力 | 写脚本是本职；有约束力的只有 `readonly` 和由人点确认的 `ask` |

### 命名

- npm 上 `godot-cli` 已被占用（见"同类项目"），`gd` 是一个图形库的包名。包名暂定 `gdcli`，查询时未被注册；**发布前要再确认并尽早占名**。
- 可执行文件名与包名无关，仍是 `gd`。已知冲突：oh-my-zsh 的 git 插件把 `gd` 设为 `git diff` 的别名。别名只在交互式终端生效，智能体和脚本不受影响；对人的影响在发布前评估，备选是同时提供 `gdcli` 这个长名字。
- 名字集中在 `cli/package.json` 的 `bin` 和插件目录名两处，改名成本低，但只限首次发布之前。

### 本项目的差异点

1. **标准版 Godot 即可用**：纯 GDScript 桥接，不要 .NET，不要 Python，编辑器侧零依赖。
2. **命令行优先**：`gd` 本身是完整产品，能进脚本和持续集成；MCP 只是它的另一种外壳。
3. **离线通道**：没开编辑器也能运行、检查、导出、查接口。上表多数项目只有在线一条路。
4. **不联网、不要账号**：只有本机回环上的 HTTP。
5. **技能与知识**：原生模块积累的 445 条易错点、接口速查、领域提示词，整理成插件的参考资料；加评测集持续度量。

### 可借鉴之处

- hybridindie 的命令实现（MIT）覆盖面很广。写第 3 阶段的修改类命令前先读它的做法，借鉴时保留版权声明。桥接的核心（服务、锁文件、认证、注册表）体量小且就是协议本身，自己写。
- 它们普遍采用的做法本项目也采用：修改走撤销栈、空跑、破坏性操作确认、结构化错误码。

## 从原生模块复用的资产

不复用代码，复用内容：

- 445 条易错点（`ai_gotchas_index.cpp`）、接口速查（`ai_api_doc_loader.cpp`）、领域提示词（`ai_domain_prompts.cpp`）、基础提示词（`ai_system_prompt.cpp`）：按主题拆成 `plugin/skills/*/references/`。
- "运行场景、收集报错"的闭环：变成 `gd run`。
- 检查点：改用编辑器自带的撤销栈。

## 不做的事

- 不做远程访问。桥接只监听回环地址。
- 不做 Godot 的安装和版本管理。`gd` 只负责找到已有的可执行文件。
- 不支持 Godot 3.x。
- 第 1 版不做运行中游戏的实时检视（需要调试器协议），只做启动、收集输出、结束。
